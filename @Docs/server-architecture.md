# Python Server 架构文档

---

## 1. 架构定位与职责边界

### 1.1 Python Server 在整个系统中的角色

**Python Server (FastAPI)** 是系统的**聊天核心引擎**，专门处理实时对话和智能记忆管理。

```
外部客户端(微信/Telegram等) 
    ↓ HTTP POST
Python Server (聊天引擎)
    ↓ 读写
Supabase 数据库 (共享存储)
    ↑ 读写
Next.js API (管理后台)
    ↑ HTTP
管理员 Web 界面
```

### 1.2 核心职责

✅ **Python Server 负责**：
- 接收外部聊天客户端的消息（微信机器人、Telegram 等）
- 构建智能上下文（三层记忆模型 + 角色人设 + 知识库）
- 调用 LLM 生成个性化回复
- 异步分析对话，提取记忆并更新用户画像
- 管理向量检索（查询 Episodic、Character、Knowledge）

❌ **Python Server 不负责**：
- 管理后台的 CRUD 操作（由 Next.js API 处理）
- 数据的向量化生成（由 Edge Function 异步处理）
- 前端界面渲染（由 Next.js 处理）

### 1.3 关键设计原则

1. **解耦架构**：Python Server 与 Next.js 永不直接通信，通过共享数据库交换数据
2. **异步处理**：记忆分析不阻塞对话，保证响应速度
3. **向量检索**：在 Server 层完成（而非依赖数据库函数），灵活控制检索逻辑
4. **无状态设计**：可水平扩展，支持多实例部署

## 2. 核心业务流程

### 2.1 聊天处理流程（主流程）

**API 端点**：`POST /api/messages`

**请求参数**：
```json
{
  "platform": "wechat",        // 平台名称
  "username": "user123",       // 平台用户标识
  "language": "zh",            // 语言(zh/en/vi)
  "message": "你好",           // 用户消息
  "model": "gpt-4o-mini"      // 可选：指定模型
}
```

**处理步骤**：

```
1. 查找/创建用户 (platform + username)
        ↓
2. 构建上下文 (context_builder)
   - 并行获取：最近对话、用户画像、角色信息
   - 向量检索：Episodic 记忆、Character 人设、Knowledge 知识库
   - 组装 System Prompt + 历史对话
        ↓
3. 调用 LLM 生成回复
        ↓
4. 保存消息（用户消息 + AI 回复）
        ↓
5. 异步触发记忆分析 (不阻塞响应)
        ↓
6. 返回 AI 回复给客户端
```

### 2.2 记忆分析流程（异步后台任务）

**触发条件**（满足任一即触发）：
- 未处理消息数 ≥ 阈值（如 18 条）
- 距离上次消息时间 ≥ 阈值（如 30 分钟）且有未处理消息

**处理步骤**：

```
1. 检查触发条件
        ↓
2. 获取未处理消息（附带少量已处理消息作为上下文）
        ↓
3. 并行执行两个任务：
   ├─ Profile 更新 (profile_updater)
   │  - LLM 分析：是否有稳定的身份信息需要更新
   │  - 区分：稳定属性(Profile) vs 事件(Episodic)
   │  - 更新用户画像（带乐观锁防并发）
   │
   └─ Episodic 提取 (episodic_extractor)
      - LLM 提取：具体事件、经历、故事
      - 去重检查：与已有记忆对比（new/update/skip）
      - 重要性评分：过滤低价值记忆
      - 写入数据库（embedding=NULL，触发向量化）
        ↓
4. 标记消息为已处理
```

## 3. 模块设计与职责

### 3.1 文件结构

```
server/
├── index.py              # FastAPI 应用入口，定义路由和主流程
├── config.py             # 配置管理（环境变量、常量、阈值）
├── utils.py              # 工具函数（日志、重试机制、格式化）
│
├── clients/              # 外部服务客户端
│   ├── db_client.py      # 数据库操作（asyncpg 直连）
│   ├── openai_client.py  # OpenAI API 调用（LLM + Embedding）
│   └── vector_search.py  # 向量检索（在 Python 层计算相似度）
│
└── tasks/                # 业务任务模块
    ├── context_builder.py    # 构建 LLM 上下文（三层记忆 + 知识库）
    ├── profile_updater.py    # 用户画像更新（异步任务）
    └── episodic_extractor.py # 情景记忆提取（异步任务）
```

### 3.2 核心模块职责

#### **index.py - 应用入口**
- 定义 FastAPI 路由 (`/api/messages`)
- 协调主流程：上下文构建 → LLM 调用 → 消息保存 → 异步记忆分析
- 管理应用生命周期（数据库连接池初始化/关闭）

#### **clients/db_client.py - 数据库客户端**
- 使用 **asyncpg** 直连 PostgreSQL（绕过 Supabase SDK，更高性能）
- 提供数据操作接口：
  - 用户管理：查找/创建用户
  - 消息操作：插入、查询、标记已处理
  - Profile 操作：读取、更新（带乐观锁）
  - Episodic 操作：插入、更新记忆
  - Prompt/Character 查询

#### **clients/openai_client.py - OpenAI 客户端**
- 封装 OpenAI API 调用：
  - `chat_completion()`：标准对话生成
  - `chat_completion_json()`：结构化数据提取（Episodic）
  - `generate_embedding()`：生成查询向量（带缓存优化）
- 重试机制：自动处理 API 错误和限流

#### **clients/vector_search.py - 向量检索**
- **关键设计**：在 Python 层面执行向量检索，而非数据库函数
- 检索流程：
  1. 从数据库获取所有候选向量
  2. 在 Python 中计算余弦相似度
  3. 过滤、排序、返回 top-k 结果
- 支持的检索类型：
  - Episodic Memory（情景记忆）
  - Character Vectors（角色人设维度）
  - Knowledge Scripts（话术库）
  - Knowledge Abbreviations（缩写库）

#### **tasks/context_builder.py - 上下文构建器**
- **核心功能**：为 LLM 组装完整的 Messages 数组
- **三层记忆模型**：
  1. **短期记忆**：最近 N 条对话（Working Memory）
  2. **语义记忆**：用户画像 Profile（Semantic Memory）
  3. **情景记忆**：向量检索相关事件（Episodic Memory）
- **增强信息**：
  - **Character Facets**：向量检索匹配的角色人设维度
  - **Knowledge Scripts**：向量检索相关话术模板
  - **Knowledge Abbreviations**：向量检索相关缩写说明
- **性能优化**：并行获取所有数据（7 个 I/O 操作同时执行）

#### **tasks/profile_updater.py - 画像更新器**
- 分析对话中的**稳定、长期身份信息**
- **区分原则**：
  - ✅ Profile：稳定属性（职业、爱好、性格等）
  - ❌ Episodic：具体事件（去了哪里、做了什么）
- **更新策略**：
  - LLM 判断是否需要更新（"NO_UPDATE" 或返回新 Profile）
  - 使用乐观锁防止并发冲突

#### **tasks/episodic_extractor.py - 记忆提取器**
- 提取对话中的**具体事件、经历、故事**
- **提取标准**：
  - 有明确时间点或时期
  - 一次性发生（非长期状态）
  - 叙事性、情节性
  - 脱离对话也能理解
- **去重机制**：
  - 检索已有相似记忆（相似度 ≥ 阈值）
  - LLM 判断：完全重复(skip) / 补充细节(update) / 全新事件(new)
- **重要性评分**：过滤低价值记忆（阈值可配置）

## 4. 三层记忆模型详解

### 4.1 设计理念

模拟人类记忆系统，让 AI 具备**短期记忆、长期知识、重要经历**：

```
用户消息 → LLM
         ↑
         |
    System Prompt (包含三层记忆)
         |
    ┌────┴────┬──────────┬────────────┐
    │         │          │            │
短期记忆   语义记忆   情景记忆    角色+知识库
(最近对话) (用户画像) (重要事件)  (人设+话术)
```

### 4.2 各层记忆的作用

| 记忆类型 | 内容 | 来源 | 作用 |
|---------|------|------|------|
| **短期记忆** | 最近 20 条对话 | 直接查询数据库 | 保持对话连贯性 |
| **语义记忆** | 用户画像（Profile） | 从对话中持续更新 | 了解用户是谁（身份、职业、爱好） |
| **情景记忆** | 重要事件（Episodic） | 从对话中提取，向量检索 top-5 | 回忆相关经历，增强共情 |
| **角色人设** | Character Facets | 向量检索 top-3 相关维度 | 动态匹配角色特质 |
| **话术知识** | Scripts + Abbreviations | 向量检索相关话术和缩写 | 提供专业回答和术语解释 |

### 4.3 记忆更新时机

- **短期记忆**：每次对话实时更新（保存新消息）
- **语义记忆**：异步更新，满足阈值后触发
- **情景记忆**：异步提取，满足阈值后触发

## 5. 向量检索机制

### 5.1 职责划分

| 环节 | 负责模块 | 说明 |
|------|---------|------|
| **存储向量化** | Edge Function | 数据插入时触发，异步生成 embedding |
| **查询向量化** | Python Server (openai_client) | 实时生成查询向量 |
| **向量检索** | Python Server (vector_search) | 在 Python 层计算相似度 |

### 5.2 为什么在 Python 层做检索？

**优势**：
1. **业务灵活性**：可自由组合过滤条件（重要性 + 相似度）
2. **完整上下文**：Server 拥有完整的业务逻辑
3. **解耦设计**：不依赖数据库特定函数，便于迁移

**实现方式**：
```
1. 从数据库获取所有候选记录（WHERE embedding IS NOT NULL）
2. 在 Python 中计算余弦相似度
3. 按相似度排序，过滤低于阈值的结果
4. 返回 top-k 结果
```

## 6. 与其他系统的交互

### 6.1 与 Supabase 数据库的交互

**连接方式**：
- 使用 **asyncpg** 直连 PostgreSQL（IPv4 直连，更稳定）
- 使用 Service Role Key 绕过 RLS（Row Level Security）

**主要操作**：
- **读取**：用户信息、消息历史、Profile、Episodic、Prompt、Character、Knowledge
- **写入**：新消息、新记忆、更新 Profile
- **触发器**：插入记忆时自动调用 Edge Function 生成向量

### 6.2 与 Edge Function 的交互

**交互方式**：通过数据库触发器间接触发（无需直接调用）

**向量化流程**：
```
Python Server 插入记录 (embedding=NULL)
        ↓
数据库触发器检测到新记录
        ↓
调用 Edge Function (HTTP Webhook)
        ↓
Edge Function 生成向量并写回数据库
```

**关键特性**：
- Python Server **无需等待**向量生成完成
- 完全异步，不影响聊天性能
- 向量化失败不会影响核心功能

### 6.3 与 OpenAI API 的交互

**调用场景**：
1. **对话生成**：发送 Messages 数组，获取 AI 回复
2. **结构化提取**：强制 JSON 输出（Episodic 提取）
3. **向量嵌入**：生成查询向量（用于检索）
4. **记忆分析**：Profile 更新判断、Episodic 去重判断

**优化措施**：
- Embedding 缓存（避免重复生成相同文本的向量）
- 自动重试机制（处理 API 限流和错误）

## 7. 关键设计亮点

### 7.1 双阈值触发机制

**问题**：何时触发记忆分析？既不能太频繁（浪费资源），也不能太迟（遗漏信息）

**解决方案**：双条件触发（满足任一即可）
- **条件 1**：未处理消息数 ≥ 阈值（如 18 条）→ 对话量达标
- **条件 2**：距上次消息 ≥ 时间阈值（如 30 分钟）且有未处理消息 → 对话暂停

**保护机制**：未处理消息超过上限（如 30 条）时，强制跳过最旧消息，避免卡死

### 7.2 任务重试与协调

**设计目标**：保证记忆分析的可靠性

**实现方式**：
- Profile 更新和 Episodic 提取**并行执行**
- 单个任务失败时**独立重试**（最多 3 次）
- 两个任务都成功才标记消息为已处理

### 7.3 乐观锁控制

**问题**：多实例部署时，如何防止 Profile 并发更新冲突？

**解决方案**：
1. 读取 Profile 时记录 `updated_at` 时间戳
2. 更新时检查 `WHERE updated_at = old_value`
3. 如果时间戳已变，说明被其他实例更新过，放弃本次更新

### 7.4 Episodic 智能去重

**问题**：如何避免重复记录相似的事件？

**解决方案**：三步去重
1. **前置检索**：找出相似度 ≥ 阈值（如 0.8）的已有记忆
2. **LLM 判断**：分析是完全重复、补充细节、还是全新事件
3. **执行动作**：
   - `skip`：完全重复，跳过
   - `update`：补充细节，更新已有记忆
   - `new`：全新事件，插入新记忆

## 8. 部署与扩展

### 8.1 部署要点

**推荐平台**：Railway / Render / Fly.io（支持 Docker）

**环境变量**（核心）：
- `POSTGRES_IPV4_URI`：数据库连接地址
- `OPENAI_API_KEY`：OpenAI API 密钥
- 其他配置见 `config.py`（有详细注释）

**启动命令**：
```bash
uvicorn index:app --host 0.0.0.0 --port 8000
```

### 8.2 扩展性

**水平扩展**：
- Python Server 是无状态的，支持多实例部署
- 使用负载均衡器分发请求
- 乐观锁机制保证数据一致性

**性能优化方向**：
- Redis 缓存 Profile（减少数据库查询）
- 批量生成查询向量（减少 OpenAI API 调用）
- 数据库连接池调优

## 9. 总结

### 9.1 架构特点

✅ **职责清晰**：聊天引擎专注于对话和记忆，不涉及管理功能  
✅ **智能上下文**：三层记忆 + 向量检索，提供个性化对话体验  
✅ **异步设计**：记忆分析不阻塞响应，保证用户体验  
✅ **完全解耦**：与管理后台通过数据库通信，独立部署  
✅ **灵活可扩展**：无状态设计，支持水平扩展  

### 9.2 业务价值

1. **个性化对话**：基于用户画像和历史记忆，提供定制化回复
2. **长期记忆**：记住重要事件，像真人一样能回忆过往
3. **角色扮演**：动态匹配角色特质，提供沉浸式体验
4. **知识增强**：话术库和缩写库提升专业性和准确性
